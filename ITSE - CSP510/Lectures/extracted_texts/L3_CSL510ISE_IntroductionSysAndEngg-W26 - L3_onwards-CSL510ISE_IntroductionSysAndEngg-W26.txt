Anecdote: The Train That Never Stopped at Night
Context:
This occurred in a European city’s newly automated
metro system. The system was highly advanced —
featuring real-time scheduling, AI-driven energy
optimization, and automated train control. No drivers.
All logic coded. All systems tested.
The Incident:
One winter night, the last train of the day was supposed
to stop at Station X — a suburban residential area.
Passengers waited on the platform.
But the train didn’t stop.
This happened again the next night. And again.
Complaints poured in.
Engineers checked the train software — it was working.
The station systems — all ﬁne.
No errors in the logs.
Finally, a system behavior specialist stepped in to
analyze not just the parts, but the whole.

The Root Cause: Emergent Behavior
Here’s what they discovered:
•The AI scheduling module was designed to optimize energy usage.
•At night, when few passengers were detected on the platform (based on infrared
sensors), and if the train was behind schedule, the AI skipped the station to
conserve power and maintain timetable.
•The system was not malfunctioning — it was behaving exactly as designed.
•But it was doing something no human intended — leaving behind actual waiting
passengers in the dark.
The sensors failed to detect passengers wearing thick winter coats, standing still in the
cold — making them appear invisible to the thermal system.

Systems Engineering Insight:
Takeaway:
The system didn’t crash. It behaved — but the behavior was emergent, based on subtle
interactions between sensors, algorithms, and assumptions.

This is why behavior modeling and scenario-based analysis are critical.
You must ask:
•What does the system do over time, under varying conditions?
•What if inputs are wrong, or incomplete?
•What feedback loops exist, and are they trustable?

Concept of ‘Components’ of the Systems

Up to now, we have established a conceptual foundation for
understanding how systems act and are perceived — Function, State,
Situation, Behavior, and Process — all of which describe what the
system is for and how it operates.
But before we can meaningfully talk about strategy or analyse a
system as a whole, we need to understand:
What the system is made of — its Components — and how those
components interact.

Why moving to Components now makes sense

1.Bridges to the 'System' as a Whole
◦Components are the building blocks whose relationships and interactions produce
the behaviors we’ve already discussed.

2.Connects to the Concept of Architecture
◦Strategy in Systems Engineering often involves reconﬁguring or optimizing
components.
3.Foundation for Trade-off Analysis
◦Without knowing the components, we can’t evaluate redundancy, failure points,
scalability, or cost-performance trade-offs.
4.Natural Progression for our Lecture Flow
◦We’ve covered dynamic/systemic concepts (state, process, etc.).
◦Next step: structural concepts (components, interfaces, interconnections).
◦Then we can unify both into a strategic system analysis.

Key Points to Cover in Components Discussion

•Deﬁnition: A component is a physical or logical part of a system, with
deﬁned boundaries and responsibilities.
•Types: Hardware, software, human, environmental, informational.
•Interfaces: How components exchange material, energy, or information.
•Hierarchy: Components → Subsystems → System.

•Coupling & Cohesion: Tight vs. loose coupling, functional cohesion.
•Failure Modes: How component-level failure affects the whole system.

Deﬁnition – What is a Component?
Set of components meets the following requirements*:
1.The properties and behavior of each component of the set have an effect on the properties
and behavior of the set as a whole.
2.The properties and behavior of each component of the set depend on the properties and
behavior of at least one other component in the set.
3.Each possible subset of components meets the two requirements listed above; the
components cannot be divided into independent subsets.
- Components of a system may themselves be systems, and every system may be part of
a larger system in a hierarchy

* requirements ensure that the set of components constituting a system always has some
property, or behavior pattern, that cannot be exhibited by any of its subsets acting alone.

A component in Systems Engineering is:
A distinct physical or logical part of a system, with deﬁned boundaries,
responsibilities, and interfaces, contributing to the system’s functions.
— adapted from INCOSE SE Handbook (2023)
Key elements:
•Physical or Logical – could be tangible (pump, CPU) or abstract (encryption
algorithm, database schema).
•Boundaries – deﬁnes what’s inside, what’s outside.
•Responsibilities – the role in achieving one or more system functions.
Example (CSE): In a distributed database system, a storage node is a component
with the responsibility to store and retrieve data blocks.
Reference:

• INCOSE Systems Engineering Handbook, 5th Ed., Ch. 3.
• Maier, M.W., Rechtin, E. (2009). The Art of Systems Architecting. CRC Press.

Coupling & Cohesion

•Coupling: Degree of dependency between components.
◦Tight coupling – components heavily depend on each other’s internal details
(riskier to change).
◦Loose coupling – components interact via minimal, well-deﬁned interfaces (more
robust).
•Cohesion: Degree to which responsibilities of a component belong together.
◦High cohesion – component’s functions are closely related (good).
◦Low cohesion – scattered responsibilities (bad for maintainability).
Example (Software Engineering):
Microservices architecture → aims for loose coupling + high cohesion.
Reference:

•Stevens, W.P., Myers, G.J., Constantine, L.L. (1974). Structured Design. IBM
Systems Journal.

•Hardware failure (disk crash)
•Software fault (memory leak, null pointer exception)
•Human error (misconﬁguration)
•Interface failure (API timeout, packet loss)
•Data failure (corrupted training dataset)
Why important:
•Supports Failure Modes and Effects Analysis (FMEA).
•Helps design redundancy and recovery strategies.

•Stamatis, D.H. (2003). Failure Mode and Effect Analysis: FMEA from Theory to

What is Strategy in Systems Engineering?
In Systems Engineering, Strategy is the planned set of decisions and guiding principles
that determine how the system achieves its mission under varying conditions.
It answers questions like:
•How will the system handle uncertainty?
•What will be done when key components fail?
•How will it scale when demand surges?
•How will it adapt when its operating environment changes?

In design, engineers model behaviors to predict resilience, failure, or efﬁciency.

Trigger: Soil moisture < threshold or scheduled time.

•Function = the intended purpose of the system, expressed as

Methodology for Identifying Functions in a System (Systems Engineering)

How Functions Guide Design

•Functions are like the North Star: all states, situations, behaviors, and
processes must serve them.

•Functions also help deﬁne KPIs → if KPIs aren’t being met, processes
may be optimized, but the system is failing its function.

1.Express in Input → Output terms
◦Identify what the system takes in and what it delivers.
◦E.g., Input = soil condition, Output = water delivered to maintain target.
2.Generalize Beyond Implementation
◦Function should be solution-neutral.
◦E.g., Function = “Provide irrigation control” (not “Run pump motor”).
3.Check Measurability
◦Link function to KPIs (how do we know the function is fulﬁlled?).
◦E.g., soil moisture kept within band 80% of time.
4.Validate with Scenarios
◦Verify: Does this function hold in normal + stressed + degraded conditions?

1.Clarify Stakeholders & Needs
◦Ask: “Who uses or depends on the system? What do they expect it to deliver?”
◦E.g., farmer → “I want consistent crop health with minimal water waste.”
2.Deﬁne System Boundary & Environment
◦What’s inside (controllable) vs. outside (external)?
◦E.g., sensors, pumps, controller (inside); weather (outside).
3.Abstract Purpose from Processes
◦Don’t confuse steps with function.
◦E.g., “Measure soil moisture” is a process, not a function.
◦Function is: Maintain optimal soil moisture.

Why Functions Are the Best Way to Build Systems

Functions in Systems Engineering: A Higher Abstraction

•A system function = the purpose the system delivers to its environment.
•It’s not about code reuse but about mission clarity.
•Example:
◦Irrigation system → “Maintain soil moisture.”
◦Hospital IT system → “Provide safe, reliable patient data access.”
•Just like programming functions, system functions:
◦Break down big complexity into manageable roles.
◦Allow decomposition into sub-functions (hardware, software, human).
◦Are veriﬁable (via KPIs, not just test cases).
Key message: Functions scale the same philosophy from code → to whole systems.

Why “Function First” is Powerful

•Purpose-driven design: Function deﬁnes why before how.
•Flexibility: Implementation can change, but the function remains.
◦Example: Flight navigation function can be realized by sextant,
GPS, or AI autopilot — function = constant,
implementation = evolving.
•Universality: Functions apply equally to biological, social, and
technical systems.
◦Heart: function = pump blood.
◦Internet: function = move information.
◦Democracy: function = distribute power/accountability.

Natural Evolution as Context

•In evolution, functions emerge ﬁrst, structures follow.
◦Eye → function = sense light, then evolved multiple structural designs
(compound eyes in insects, camera eyes in humans).

◦Wing → function = enable movement through air, then implemented as
bird feathers, insect membranes, bat skin.
•Lesson: Nature doesn’t evolve organs ﬁrst; it evolves functions that
matter for survival.
◦Structure changes, but function endures.
Key point: “Just as evolution favors functions that help survival, engineers
must deﬁne functions that ensure usefulness and resilience.”

Contextualizing for Us:

•As Programmers: Functions = reusable building blocks.
•As Engineers: Functions = guiding purposes that hold designs together.
•As Future Leaders: Functions = the ability to ask “What is the purpose?” before
“How do we do it?”.
This knowledge contextualizes into:
•Software Engineering: Write better requirements.
•Systems Engineering: Design more resilient systems.
•AI/Agentic Systems: Teach machines not just to react, but to serve functions under
constraints.
•Life: Always(most of the time) ask the “why” before jumping into the “how.”

Conclusion:
Functions are the best way to build anything — from a small program, to a
hospital IT system, to life itself.
Because they deﬁne purpose.
